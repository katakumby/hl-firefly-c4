## How to read the flow catalog

Every entry corresponds to one named DSL relationship `unleash_<flowId>` and
stable property `architecture.id = unleash.flow.<flowId>`. The arrow points from
the initiator to the service/store it invokes, or from an event producer to its
consumer. Request/response arrows include the returned information in their data
description; reverse arrows are not added just to show ordinary responses.

Container summaries and component projections describe the same exchanges at
different C4 levels, not additional network calls. In-process edges aggregate
module/service/store interactions; JavaScript promises and Rust async calls do
not imply a queue or broker. “Awaited” means the caller awaits completion.
Relationship evidence is explicitly classified as a logical dataflow inferred
from pinned implementation; the DSL carries the source URLs for both endpoints.

“Persistence” below records what becomes durable or remains volatile. It does not
add an atomicity, retry, delivery or failover guarantee that the implementation
does not provide. Context used for frontend evaluation stays in that evaluator;
usage metrics represent counts and metadata, not a stream of per-user contexts.
